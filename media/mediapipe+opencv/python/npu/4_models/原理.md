# 手势识别 NPU 四模型流水线 — 原理详解

> 对应代码：`hand_npu_4_models.py`（推理库）、`gesture_tracker_4_models.py`（demo）
> 硬件：Firefly RK3588（RKNPU2，librknnrt 2.3.2）；模型源自 Google MediaPipe `gesture_recognizer.task`
> 本文讲清楚：每个模型做什么、坐标怎么变换、手势是怎么从 21 个点变成 8 个标签的、以及每一步为什么这么设计。

---

## 1. 系统总览

```
相机帧(BGR 640×480)
  │  rotate 180°(摄像头倒装) + cvtColor → RGB
  ▼
┌─ 有追踪缓存? ──是──> 用上一帧21点直接构ROI ──┐        (省掉palm推理, 3次NPU推理)
│        │否                                    │
│        ▼                                      │
│  [模型1] palm检测 (192×192输入)                │   找到手掌粗框
│        ▼                                      │
│  palm框 → 仿射ROI(旋转+缩放到224) ←──────────┘
│        ▼
│  [模型2] 关键点 (224×224输入)                  →  21个关键点(x,y,z) + 手置信度 + 左右手 + 世界坐标
│        ▼
│  [模型3] 手势嵌入 (21×3 → 128维)              →  把关键点编码成128维向量
│        ▼
│  [模型4] 手势分类 (128 → 8类概率)             →  7种固定手势 + None
▼
画面叠加: 骨架(仅固定手势成立时) + 标签
```

四个模型全部来自官方 task 包解包出的 4 个 tflite，在 x86 服务器上用 rknn-toolkit2 转成 .rknn 后放到板上 NPU 跑。实测整条链路（抓图→识别完成）9~16ms，摄像头 30fps 跑满。

**为什么要 4 个模型？** 这是 MediaPipe 的经典两级设计：
- **检测贵**（在全图找手），**追踪便宜**（手不会瞬移）。所以先粗检测，后续帧直接用上一帧结果构 ROI 只跑关键点，追踪失败才回退全流程。
- **关键点模型只懂"手"**，不懂"手势"；手势由嵌入+分类两个小模型负责（共约 9 万次乘加，转 NPU 后单帧 <1ms）。

## 2. 坐标系约定（整个系统最容易出错的地方）

### 2.1 图像归一化坐标

所有对外输出的关键点 `pts` 是 `(x, y, z)`：

- `x = 像素X / 帧宽`，`y = 像素Y / 帧高` —— 0~1 归一化，与帧分辨率无关；
- `z = raw_z / 224` —— 关键点模型输出的是 224 裁剪空间里的原始 z，除以 224 归一化。
  - **腕为原点**（z≈0），**朝相机方向为负**；
  - 量级与 x/y 同尺度（手掌前后起伏约 ±0.1~0.3）。
  - ⚠️ 历史教训：这里曾写成 `raw_z × 2.5 / 224`，z 放大 2.5 倍直接让手势分类乱出标签（z 占嵌入模型输入的 21/63 维，见 §5）。**z 的尺度必须和官方一致，不能随手乘系数。**

### 2.2 21 点拓扑（MediaPipe 通用）

```
0腕  1-4拇指(根→尖)  5-8食指  9-12中指  13-16无名指  17-20小指
每指4点: 掌指关节MCP → 近指间PIP → 远指间DIP → 指尖TIP
```

骨架连线表 `CONNS` 就是按这个拓扑连的。

### 2.3 旋转与镜像

- 摄像头物理倒装，进管线先 `rotate 180°`，用户看到的画面是正的；
- 左右手：模型按"镜像自拍"视角约定输出 handedness（sigmoid 后 ≥0.5 为 Right），而画面没做镜像，所以**显示时对调**（`handed = "Left" if hs >= 0.5 else "Right"`）。

## 3. 模型1：palm 检测器（hand_detector，BlazePalm 短程版）

**作用**：在全图里找到手掌的粗框和 7 个关键点。它是"检人先检脸"思路的"检手先检掌"——掌心区域特征稳定（不随手指张合变化），比直接检全手稳得多。

### 3.1 letterbox 预处理

640×480 等比缩到 192×144，上下各补 24 行黑边成 192×192（`_palm_rect` 开头）。模型输入固定 192，不能拉伸变形（长宽比失真会让框尺寸错）。

### 3.2 SSD anchors —— 2016 个先验框

输出不是"框的坐标"，而是**相对锚点的偏移量**。锚点铺满两个特征图：

| 特征图 | stride | 每格锚数 | 格数 | 锚数 |
|---|---|---|---|---|
| 24×24 | 8 | 2 | 576 | 1152 |
| 12×12 | 16 | 6 | 144 | 864 |
| 合计 | | | | **2016** |

锚点坐标 `((x+0.5)·stride/192, (y+0.5)·stride/192)`，尺寸恒为 1（fixed_anchor_size，只有中心位置有意义）。生成顺序必须和训练时完全一致（y 外层、x 内层、每格 n 个锚），顺序错了解码就全错位。

### 3.3 解码与筛选

模型两个输出：`[1,2016,18]`（每锚 18 数 = 框4 + 7关键点×2）、`[1,2016,1]`（分数）。

```
框中心 = (锚x + raw_x/192) · 192        框宽 = raw_w/192 · 192     (均在192画布像素)
关键点同理。分数过 sigmoid > 0.5，再贪心 NMS(IoU≤0.3) 只留置信度最高的一只手。
最后 letterbox 逆映射回原图:  x_原图 = (x_画布 - pad) / scale
```

### 3.4 palm框 → 手部ROI

关键点模型要的不是框，是一个**旋转正方形裁剪**：

1. **旋转对齐**：取 palm 关键点[腕0 → 中指根2]，把这条向量旋转到竖直向上（θ = π/2 − atan2(−Δy, Δx)）——让每只手进模型时姿态尽量一致，这是模型精度的前提；
2. **上移半高**：palm 框只框住掌心不含手指，沿旋转后的 -Y 上移半框高，让手指也进裁剪；
3. **扩方**：长边 ×2.6 成正方形（留足指间空隙），换算缩放 s = 224/side；
4. 生成 224 仿射矩阵 `M = [[s·c, s·d, tx], [−s·d, s·c, ty]]`，`cv2.warpAffine` 裁出 224×224。

## 4. 模型2：关键点模型（hand_landmarks_detector）

**输入**：224×224 裁剪。**输出 4 个张量**（顺序固定，`_split_lm` 按最后一维长度分拣）：

| 输出 | 形状 | 含义 |
|---|---|---|
| lm | [1,63] | 裁剪空间 21×3 关键点（224 像素单位） |
| flag | [1,1] | 手置信度 logit → sigmoid ≥0.5 才认为裁剪里真有手 |
| hand | [1,1] | 左右手 logit（只用于显示） |
| world | [1,63] | 世界坐标 21×3（以腕为原点的米制，透传给上层） |

### 4.1 解码：从裁剪空间回原图

裁剪是"绕 ROI 中心旋转 θ 再缩放 s"，逆变换：

```python
dx, dy = 裁剪点 - (112, 112)          # 224裁剪里的偏移
px = ROI中心x + (c·dx − d·dy) / s     # 旋转逆映射(转回θ角前)再除缩放
py = ROI中心y + (d·dx + c·dy) / s
```

### 4.2 坏帧守卫（`_run_landmark` 末尾）

裁剪质量差（手不全、模糊）时模型可能输出**天文数字坐标**（有限值但巨大，画到 cv2 直接崩：cv2 5.0 只收 int32 范围内的纯 int）或 nan/inf。守卫：**非有限值或超帧尺寸 4 倍 → 视为本帧追踪失败**，返回 None，让上层同帧回退 palm 全流程，且不污染追踪缓存。

### 4.3 ROI 追踪（`_roi_from_landmarks`）

有上一帧 21 点时，跳过 palm 直接构 ROI：

- 旋转对齐：腕(0)→中指根(9) 对齐 Y 轴（比 palm 的 7 点更准）；
- 尺寸：21 点**旋转包围盒** ×2.0（包围盒已含全手，放大系数比 palm 的 2.6 小；下限 56px 防手贴镜头时退化）；
- 中心：包围盒中心。

**逆旋转公式（曾经的大 bug）**：旋转坐标 u,v 是绕**图像原点**算的绝对坐标：

```
u =  c·x + d·y     v = −d·x + c·y        (正变换)
x =  c·um − d·vm   y =  d·um + c·vm      (逆变换, 原点自动抵消)
```

错误写法 `cx = x0 + c·um − d·vm` 会把整个腕向量位移进 ROI 中心 → 裁剪跑到手外 → 幻影坐标每帧翻倍复合（日志特征：坐标 ×2 递增、hs 冻结）。减掉这个位移就对了——**u,v 的逆变换不需要任何参考点**。

### 4.4 z 坐标的意义

z 让"手指朝向相机/背离相机"可区分（比如握拳 vs 手掌在侧视角下 2D 几乎一样，靠 z 区分）。它会被原样喂给手势嵌入模型，所以**尺度必须精确**（§2.1 的教训）。

## 5. 模型3：手势嵌入（gesture_embedder）—— 本系统最精巧的部分

**作用**：把 21 个点（63 个数）压缩成 128 维向量，让"同一个手势的不同手、不同位置、不同大小"落在向量空间相近的位置。

### 5.1 输入：只有 hand 活着

tflite 声明 3 个输入（hand / handedness / world_hand），但对计算图做**可达性分析**证明后两个没有任何算子消费——是死输入。RKNN 导出时正确剪掉，板上 runtime 只有 1 个输入，推理只喂 `hand(1,21,3)`。（喂 3 个会直接报 `index >= input_num` 错误洪水。）

### 5.2 归一化：6 点定标（op0~op15，43 个算子里的前 16 个）

```
① gather 手掌6点:  indices=[0,1,5,9,13,17]  (腕 + 5个掌指关节, axis=-2) → [1,6,3]
② 求均值 mean      → 掌心中心 μ [1,1,3]
③ 全部21点减 μ     → 平移归零（位置无关）
④ x跨度 = max(x)−min(x), y跨度 = max(y)−min(y)     (只用x/y, z不参与!)
⑤ 尺度 = max(x跨度, y跨度) + 1e-5   (eps防除零)
⑥ 除以尺度         → 尺度无关（远近无关）
⑦ reshape [21,3] → [63]   (顺序: x0..x20, y0..y20, z0..z20)
```

结论：嵌入对**平移、手掌大小完全不变**；但**对旋转敏感**（不做旋转移除——手 tilted 时特征会变）且 **z 的绝对尺度敏感**（z 被 x/y 跨度除，x/y 不变时 z 的系数就是它的"相对权重"）。这就是 z×2.5 事故的原理：z 被 2.5 倍放大后，网络看到的输入整体畸变，分类器输出完全乱掉（同一帧从 Open_Palm(0.53) 变 None(0.93)）。

### 5.3 主干：BN 折叠的残差 MLP（op16~op42）

不是循环网络，就是一个 7 层残差全连接（128 维）：

```
h0 = reshape后的63维
shortcut = FC(h0, W_dense12, b_dense12)            # 原始捷径(无激活)
branch   = ReLU(FC(h0, W', b'))                    # 同输入但BN已折叠进权重
h1 = shortcut + FC(branch, W_dense13, b_dense13)

重复6个块 (batch_normalization_11~16 / dense_14~18):
    y  = ReLU(h1 · γk + βk)        # BN仿射
    h1 = h1 + FC(y, Wk, bk)        # 残差

嵌入 = ReLU(FC(h1, W'', b''))       # 末层FC128→128, fused RELU → 128维全非负
```

**BN 折叠**是理解这张图的关键：训练时是 `dense → batchnorm → relu`，BN 对全连接输出是逐通道仿射 `y = γ⊙x + β`，转换工具把它并进了下一层的权重：

```
W' = W · diag(γ)      b' = γ ⊙ b_dense + β
```

所以图里会出现**同一输入接两个 FC**（一个原始 W 作捷径，一个折叠后的 W' 作主路）——RKNN 转换时这类重复结构要小心（实测本例转换是忠实的，见 §7）。

fused RELU 存在性藏在算子 options 的字节 0（1=RELU）；tflite 里没有独立的 relu 算子。

### 5.4 嵌入的性质

- 128 维、全非负、典型 L2 范数几十~百（正常手）；
- 同手势不同人/远近 → 向量相近；不同手势 → 分离明显；
- 这也是分类器敢只用一个 128→8 全连接的原因：嵌入空间已经把类间距离拉开了。

## 6. 模型4：手势分类器（canned_gesture_classifier）

只有 4 个算子：`MUL→ADD(BN仿射+ReLU) → FC(128→8) → SOFTMAX(β=1)`。输出**已经是概率分布**（8 个数和=1），代码里"和≠1 才补 softmax"只是保险。

### 6.1 视角敏感性 —— 为什么直接用官方模型会"不灵敏"（实测结论）

canned 分类器的训练数据是**掌心朝镜、手指朝上、竖直手**的标准姿态。嵌入归一化（§5.2）只除平移/尺度，**不除旋转也不除镜像**，所以：

- 手倾斜 40°（本机摄像头装得低、从下往上拍，自然姿态就是斜的）→ 特征整体偏移；
- 手背朝镜（Victory/ILoveYou 反着手做）→ 相当于换了另一只手的镜像，形状特征全反；
- 这两个因素叠加时，目标类概率直接掉到 0.00~0.12，分类器给出自信的 None。

**这不是我们管线的问题**：把同一批板端快照喂给 PC 官方 GestureRecognizer，它同样失败（Victory 时段官方全 None 0.59~0.79、ILoveYou 时段官方 None 0.88~0.96、手掌也只有 0.52~0.56 压线）。38 帧对照数据见 `/tmp/probe_exp.py` 实验记录。

### 6.2 三探针集成（`_run_gesture`/`_fuse_probs`）

对付视角敏感的办法：**几何变换 21 点后多跑几遍分类器，逐类取最大**。探针变换是纯 numpy（<0.1ms），多花的是 embedder+classifier 的小推理（合计约 +1~2ms）：

| 探针 | 变换 | 治什么 |
|---|---|---|
| 原始 | — | 标准姿态（多数帧） |
| 翻面 | `(x,z)→(−x,−z)` | 手背朝镜（相当于从另一侧看=掌背互换+换手） |
| 旋正+翻面 | 绕腕旋正（腕→中指根竖直向上）再翻面 | 手背朝镜+手倾斜的叠加情形 |

**融合规则（关键，有讲究）**：

```
fused[Thumb_Up/Thumb_Down] = max(原始, 翻面)          # 旋正探针会破坏拇指上/下语义, 不许参与
fused[其余固定手势]         = max(原始, 翻面, 旋正+翻面)
fused[None]                = max(原始, 翻面)          # 旋正探针不许投None(见§8坑9)
```

翻面对拇指是安全的（拇指向下从背面看还是拇指向下），但"旋正"对拇指类是语义错误（拇指手势的"竖直"基准不是腕→中指根方向），该探针会输出 None≈1.0——所以它只许"提名"固定手势，不许投反对票。另有一个捷径：原始探针 top1 非 None 且 ≥0.8 时跳过其余探针（标准姿态下省 4 次小推理）。

实测 38 帧重放（板上真 NPU）：识别帧的概率从大量 0.51~0.56 压线区抬到 0.57~0.93 稳区；手掌 0.48→0.65，握拳 0.62~0.70→0.84+，Thumb_Up 三帧全回。剩余不认的帧（Victory×4、ILoveYou×5）手指本身没伸直/手背朝镜加侧倾过狠，官方模型同样不认——这部分只能靠摆正手势。

demo 的防抖（`EMA_A=0.35` / `ADOPT=0.40` / `RELEASE=0.18`）：对融合概率做 **EMA 平滑 + 滞回双阈值**——平滑概率的 EMA 超过 0.40 才显示新手势、跌破 0.18 才撤下。旧的"连续 3 帧相同才采纳"计数器有个结构性缺陷：任何一帧不匹配就把计数清零，分类器在阈值边界抖动时永远凑不齐 3 帧，手势"出得慢还老掉"；EMA+滞回下单帧毛刺打不垮已成立的标签，边界抖动也不再闪烁。丢手时立即清零 EMA 和标签。骨架只在固定手势成立时绘制（与标签同进退）。

| 序号 | 类别 | 中文 | 手势 |
|---|---|---|---|
| 0 | None | 无 | 非固定手势（**按无手势处理，不显示**） |
| 1 | Closed_Fist | 握拳 | 四指收拢 |
| 2 | Open_Palm | 手掌 | 五指张开 |
| 3 | Pointing_Up | 指向 | 只伸食指向上 |
| 4 | Thumb_Down | 拇指向下 | 👎 |
| 5 | Thumb_Up | 点赞 | 👍 |
| 6 | Victory | 胜利 | ✌️ 食指+中指 |
| 7 | ILoveYou | ILoveYou | 🤟 拇指+食指+小指 |

（demo 层防抖见 §6.2：EMA 平滑 + 滞回双阈值；骨架只在固定手势成立时绘制，无手势时画面干净。）

## 7. RKNN 转换与部署

- 转换在 **x86 服务器**（rknn-toolkit2 2.3.2），目标 RK3588 NPU；板上 rknnlite 同版本。4 个 tflite 的 md5 与官方 task 包逐一核对过，转换源无误。
- **转换忠实性验证过**：用 numpy 对 tflite 原图做逐算子精确仿真，同一输入下嵌入与板上 rknn 输出 L2 差仅 0.005、8 类概率逐位一致——NPU FP16 足够这套小模型。
- 嵌入模型的死输入剪枝（§5.1）是转换时自动完成的，板上 `input_num=1`。

## 8. 已踩过的坑（按时间线，全部已修）

1. **嵌入模型死输入**：tflite 3 输入只有 1 个活；板上按 3 个喂会报错洪水。→ 只喂 hand。
2. **坏解码坐标炸 cv2**：坏裁剪帧输出天文数字坐标（有限值），×帧宽超 int32，cv2 5.0 画线直接崩。→ 守卫（§4.2）+ 绘制前 clip ±2^20。
3. **追踪 ROI 逆旋转加了腕点**：幻影坐标逐帧翻倍（§4.3）。→ 去掉参考点位移。
4. **追踪 ROI 错误上移半高**：那是 palm 路径补偿"框不含手指"的，21 点包围盒不能再用。→ 已去掉。
5. **触摸双投递**：一次点击两个 LBUTTONDOWN，PAUSE 这类 toggle 互相抵消。→ 300ms 去重。
6. **^C 被吞**：Ctrl+C 落在 NPU 推理里被 rknnlite 吞掉不退出。→ signal 处理置退出标志。
7. **z 系数 ×2.5**（最终根因，症状是"识别不到、乱变"）：z 放大 2.5 倍 → 嵌入畸变 → 分类乱标签（§5.2）。→ `pz = raw/224`，并加回归测试锁定。
8. **重放/快照帧不清追踪缓存**：快照之间隔 2 秒手已大挪，上一帧的 ROI 缓存会裁出垃圾（flag 守卫拦不住），逐帧 `eng._track_pts = None` 才对。实时流帧间连续没这个问题。
9. **探针融合让旋正探针投 None**：旋正对拇指类是语义错误，该探针输出 None≈1.0，把本已识别的 Thumb_Up(0.65) 压成 None(1.00)。→ 融合规则限定：旋正+翻面探针只许提名固定手势（类1,2,3,6,7），None/拇指两类只用原始+翻面（§6.2）。
10. **canned 模型的视角敏感性**（"识别不灵敏"的真正大头）：手背朝镜/手倾斜时官方模型自己也大面积输出 None（§6.1）。→ 三探针集成 + 摆正手势（掌心朝镜、手指朝上）。

**验证方法**（以后排查同类问题直接用）：
- **numpy 精确仿真**：手写 flatbuffer 解析器（`/tmp/tfl_sim.py`）+ 逐算子执行器（`/tmp/gsim.py`），PC 上就能精确复现 tflite 数学，用来对照板上输出；
- **官方对照**：PC 装 mediapipe 跑官方 GestureRecognizer 处理同一批帧，落盘官方 21 点和标签（`/tmp/pc_ref2.py`）；我们的关键点+正确 z 约定喂官方标签比对，10 帧 9/10 一致（唯一分歧帧官方自己置信度只有 0.52）；
- **⚠️ 诊断帧陷阱**：diag 保存的 f_*.jpg 已转过 180°，板上复现脚本**不能再转**，否则得到"关于图像中心点对称的幻影手"假象——这个问题曾把排查带进沟里（追踪、anchors、模型全被冤枉了一遍）。
