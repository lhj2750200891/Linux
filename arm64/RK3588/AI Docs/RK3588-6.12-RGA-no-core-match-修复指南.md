# RK3588（Rockchip 6.12 内核分支）RGA 老化 `no core match` 修复指南

> 适用对象：使用 firefly `common_linux6.12_next` 系 SDK（内核 6.12.x）的项目组。
> 案例平台：LGA-3588L-MINI（RK3588，**16GB** 内存，Ubuntu 24.04），内核 6.12.69（commit 623a61b4ecd7），RGA 驱动 v1.3.13，librga 1.10.5_[11]。
> 配套补丁：`rk-heaps-dma32-fix-20261010.patch`（9 个文件，基于上述树生成，`git apply` 即用；若你的树基线不同导致 apply 失败，按第 4 章手工对齐）。
> 本修复**不动 RGA 驱动、不改 QA 脚本与测试二进制**，只是把内核 dma-buf 子系统丢失的 Rockchip 官方内容恢复回去。

---

## 0. 结论速览（TL;DR）

| 项目 | 内容 |
|---|---|
| 表象 | RGA 老化一启动就刷 `rga: no core match`，几秒内 die → `AGING FATAL` |
| 直接原因 | 压测缓冲分配到了 **>4G** 物理内存，内核 RGA 策略把 RGA2 排除；而用例里有 RGA2-only 任务，无核可配 |
| 根本原因 | **6.12 分支合入快照时丢了 Rockchip 官方的 dma-buf 改动**：`/dev/dma_heap/system-uncached-dma32` 等节点对应的实现（`rk_system_heap.c`/`rk_cma_heap.c`）没被编译，两个辅助库文件干脆不在树里 |
| 修复 | ① 恢复 4 个缺失文件（page_pool / deferred-free-helper）② Makefile/Kconfig 按官方接线 ③ 对残存的 6.1→6.12 API 漂移做适配 ④ 确认 `CONFIG_DMABUF_HEAPS_SYSTEM=y`、`CONFIG_DMABUF_HEAPS_CMA=y` |
| 验证 | `ls /dev/dma_heap/` 出 6 个节点；demo 打印 `Use DMA heap /dev/dma_heap/system-uncached-dma32`；dmesg `no core match` 计数为 0 |

内存 ≥ 4GB 的机型才会暴露此问题（≤4GB 机型所有物理页都在 4G 以下，RGA2 永远可用，所以一直没被发现）。

---

## 1. 现象

老化（aging）RGA 项启动后 dmesg 持续刷：

```
rga: no core match
```

测试框架判定连续快速失败 → `die too soon` → `AGING FATAL`，整个老化流程中止。

测试进程（rgaImDemo，QA 定制 pressure 压测模式）在日志里的两种表现：

- 内核完全缺标准 heap 节点时（config 被关掉的情况）：
  `No DMA heap candidate found, pressure buffers fallback to malloc`
- 内核只有主线 system/cma heap 时（基线 defconfig 的情况）：无上述报错，静默回退到 `system-uncached`/`cma`/`system` —— 但这些堆拿到的都是 **>4G** 页面，结局相同。

---

## 2. 根源分析

### 2.1 应用层故障链

QA 的 rgaImDemo 压测模式按固定顺序尝试打开 DMA heap 设备（编译在二进制 rodata 里的候选序）：

```
/dev/dma_heap/system-uncached-dma32  →  system-uncached  →  cma  →  system
```

四个都打不开才回退 malloc。压测缓冲要求 **uncached + 物理地址 < 4G**，所以理想候选是第一个 `system-uncached-dma32`。

### 2.2 内核层：RGA 策略为何拒绝任务

`drivers/video/rockchip/rga3/rga_policy.c` 的 `rga_task_assign()` 按固定顺序逐核做能力匹配，其中一条（`rga_job.c` 依据缓冲物理地址打上 `RGA_JOB_UNSUPPORT_RGA_MMU` 标记后）：

```c
if (scheduler->data->mmu == RGA_MMU &&
    job->flags & RGA_JOB_UNSUPPORT_RGA_MMU) {
    rga_job_log(job, "RGA2 only support under 4G memory!\n");
    continue;                       /* RGA2 被排除 */
}
```

RGA2 的 MMU 只有 32 位寻址能力，缓冲物理页一旦落在 4G 以上，RGA2 直接出局。

而压测用例刻意构造了两类任务来分别压两个硬件：

| 任务类型 | 规格 | 为什么只能跑在指定核 |
|---|---|---|
| RGA3-only | 4096×4097，多 dst | 高度 4097 超过 RGA2 上限 |
| **RGA2-only** | 64×8192 → 64×4096 | 宽 64 小于 RGA3 最小宽 **68**；高 8192 超 RGA3 上限 8176 |

RGA2 被排除后，RGA2-only 任务可选核集合为空 → `optional_cores == 0` → **`no core match`**。

### 2.3 真正的病根：6.12 分支丢了官方 dma-buf 改动

Rockchip 官方内核里，`/dev/dma_heap/` 下带 `dma32` 的节点由 `drivers/dma-buf/heaps/rk_system_heap.c` 提供（注册 system / system-dma32 / system-uncached / system-uncached-dma32 四个标准命名节点，dma32 变体用 GFP_DMA32 页池），配套两个辅助库：`page_pool.c/.h`、`deferred-free-helper.c/.h`。

在我们的 6.12 分支（firefly/vendor 合入的快照）里，这套东西丢了：

| 官方状态（可对照 6.1 谱系合并提交 `60b7cdaddbf2`） | 我们 6.12 分支的现状 |
|---|---|
| `heaps/Makefile` 编 `rk_system_heap.o`（SYSTEM）、`rk_cma_heap.o`（CMA）、`page_pool.o`、`deferred-free-helper.o` | 指回主线 `system_heap.o`/`cma_heap.o`——只注册 system/system-uncached/cma，**没有 dma32** |
| `page_pool.c/.h`、`deferred-free-helper.c/.h` 在树里 | **文件整个不存在** |
| `rk_system_heap.c`/`rk_cma_heap.c` 可编译 | 文件还在，但成了没人编译的孤儿，且只适配了一半（详见 4.4） |

于是出现一个经典陷阱：**这棵树里存在注册 dma32 节点的源码，但任何 Kconfig 开关都编不到它**——它不被任何 Makefile 行引用。

### 2.4 为什么"只改内核配置"修不好（我们踩过的两轮坑）

| 内核版本 | config | 源码状态 | /dev/dma_heap | demo 行为 | 结果 |
|---|---|---|---|---|---|
| 基线 | SYSTEM=y, CMA=y（主线实现） | 官方接线缺失 | system / system-uncached / cma（无 dma32） | 回退到 system-uncached/cma → 缓冲 >4G | RGA2 被排除，`no core match` |
| 试错版 | SYSTEM=n, CMA=n, RK_SYSTEM_HEAP=y | 同上 | **空**（只剩 `/dev/rk_dma_heap/`） | 找不到任何候选 → malloc → >4G | 同样 `no core match` |
| 修复版 | SYSTEM=y, CMA=y | 官方接线 + API 适配 | 6 节点齐全（含 dma32） | 用上 system-uncached-dma32 → <4G | **全部成功** |

### 2.5 `/dev/rk_dma_heap/` 新框架为什么救不了

6.12 树里还有一套**新的** Rockchip 私有 heap 框架（`drivers/dma-buf/rk_heaps/`，节点在 `/dev/rk_dma_heap/rk-system-heap` 等）。注意它与标准框架**不是替代关系**：

- 设备节点路径不同（`/dev/rk_dma_heap/` vs `/dev/dma_heap/`）；
- ioctl 不同（`RK_DMA_HEAP_IOCTL_ALLOC`，magic `'R'`；标准是 `DMA_HEAP_IOCTL_ALLOC`）。

librga 1.10.x、QA rgaImDemo 以及大量存量用户态（MPP、相机 HAL 等）只认标准 `/dev/dma_heap/<名字>` 接口。新框架可以继续开着（两者共存、命名空间不冲突），但它**替代不了**标准节点。

## 4. 修复步骤

### 4.1 恢复缺失的 4 个文件

**方式 A：从本仓库 git 历史恢复（推荐）**

官方完整内容存在于 6.1 谱系合并提交里（firefly SDK 仓库 `--all` 可见；SHA 不同就先用上面的 `git log --all` 找等价提交）：

```bash
cd <kernel-source>
git show 60b7cdaddbf2:drivers/dma-buf/heaps/page_pool.c              > drivers/dma-buf/heaps/page_pool.c
git show 60b7cdaddbf2:drivers/dma-buf/heaps/page_pool.h              > drivers/dma-buf/heaps/page_pool.h
git show 60b7cdaddbf2:drivers/dma-buf/heaps/deferred-free-helper.c   > drivers/dma-buf/heaps/deferred-free-helper.c
git show bb97bfd3d8e8:drivers/dma-buf/heaps/deferred-free-helper.h   > drivers/dma-buf/heaps/deferred-free-helper.h
```

> 注意：60b7cdaddbf2 里的两个 `.c` 是 **6.1 时代的 API**，直接编译会报错，必须再做 4.4 的适配。只有 `.h` 两个可以原样使用。

**方式 B：直接 apply 配套补丁**

```bash
cd <kernel-source>
git apply /path/to/rk-heaps-dma32-fix-20261010.patch
```

补丁里 4 个新文件已含全部 6.12 适配，源码修改也一并带上了。基线偏差导致 context 对不上时用 `patch -p1 --fuzz=3` 或按 4.2~4.4 手工做。

### 4.2 Makefile 接线（对照官方 `60b7cdaddbf2`）

`drivers/dma-buf/heaps/Makefile` 全文：

```makefile
# SPDX-License-Identifier: GPL-2.0
obj-$(CONFIG_DMABUF_HEAPS_DEFERRED_FREE) += deferred-free-helper.o
obj-$(CONFIG_DMABUF_HEAPS_PAGE_POOL)	+= page_pool.o
obj-$(CONFIG_DMABUF_HEAPS_SYSTEM)	+= rk_system_heap.o
obj-$(CONFIG_DMABUF_HEAPS_CMA)		+= rk_cma_heap.o
obj-$(CONFIG_DMABUF_HEAPS_SRAM)	+= sram_heap.o
```

（即把 `system_heap.o`→`rk_system_heap.o`、`cma_heap.o`→`rk_cma_heap.o`，并新增两行辅助库。旧的 `system_heap.c`/`cma_heap.c` 留在树里不碍事。）

### 4.3 Kconfig 补两个库符号

`drivers/dma-buf/heaps/Kconfig` 在 `DMABUF_HEAPS_SYSTEM` 之前新增，并给 SYSTEM 加两条 select：

### 4.4 源码 6.12 API 适配（方式 A 或手工对齐时需要）

两个 `rk_*.c` 在我们分支上只适配了一半（vmap 部分被改成了主线新式签名，其余没动）。需要修的点如下——**改之前先看你树里能编译过的 `system_heap.c` 的对应写法，以它为准**：

| # | 位置 | 问题（6.1 写法） | 6.12 修法 |
|---|---|---|---|
| 1 | `page_pool.c`、`deferred-free-helper.c` | `register_shrinker(&shrinker, "name")` | 6.7 起改为 `shrinker = shrinker_alloc(0, "name")` → 逐项赋 `->count_objects/->scan_objects/->seeks/->batch` → `shrinker_register(shrinker)`；shrinker 变量改指针 |
| 2 | 两个文件的 `.vmap/.vunmap` ops | 若被改成 `void *vmap(dmabuf)` 新式签名 | 本树 dma-buf 核心是老签名：`int vmap(dmabuf, struct iosys_map *)` + `iosys_map_set_vaddr()`/`iosys_map_clear()`（照抄本树 `system_heap.c`） |
| 3 | 所有 `.allocate` 实现（每文件 2~3 处） | `fd_flags/heap_flags` 用 `unsigned long` | ops 原型是 `(struct dma_heap *, unsigned long len, u32 fd_flags, u64 heap_flags)`，改形参类型 |
| 4 | `rk_system_heap.c` | `.get_pool_size` op 及 `system_get_pool_size()` | 本树 `dma_heap_ops` 没有该成员，整体删除 |
| 5 | `rk_cma_heap.c` 错误路径 | `dma_heap_put(heap)` | 本树无此函数，删除调用（只保留 kfree，调整 goto 标号） |
| 6 | `rk_system_heap.c` `system_heap_create()` | `swiotlb_max_segment()` 块 | 函数已从内核移除；该块只是运行时收紧 `orders[]`，而 `orders[] = {8,4,0}` 已足够保守，**整块删除**（连带消除 `MAX_ORDER`→`MAX_PAGE_ORDER` 的改名问题） |
| 7 | 两个文件的 `set_heap_dev_dma()` | `err = dma_set_max_seg_size(...)` | 6.12 返回 void，直接调用即可 |

我们分支上实测会报的编译错（供对照自查）：`-Werror=incompatible-pointer-types`（#2/#3）、`has no member named 'get_pool_size'`（#4）、`implicit declaration of function 'dma_heap_put'/'swiotlb_max_segment'`（#5/#6）、`void value not ignored`（#7）、`'MAX_ORDER' undeclared`（#6）。

### 4.5 内核配置

```kconfig
CONFIG_DMABUF_HEAPS=y            # 基线已开
CONFIG_DMABUF_HEAPS_SYSTEM=y     # → select 出 PAGE_POOL / DEFERRED_FREE
CONFIG_DMABUF_HEAPS_CMA=y        # → cma / cma-uncached 节点
# 可选保留（新框架，与标准节点不冲突）：
CONFIG_DMABUF_HEAPS_ROCKCHIP=y
CONFIG_DMABUF_HEAPS_ROCKCHIP_SYSTEM_HEAP=y
```

基线 `rockchip_linux_defconfig` 本来就有 SYSTEM/CMA=y；显式写进项目 config fragment（我们是 `arch/arm64/configs/firefly-linux.config`，经 `RK_KERNEL_CFG_FRAGMENTS` 合入）是为了防基线漂移。改完在最终 `.config` 里确认 `DMABUF_HEAPS_SYSTEM=y` 且 `DMABUF_HEAPS_PAGE_POOL=y`、`DMABUF_HEAPS_DEFERRED_FREE=y` 被 select 出来。

### 4.6 编译烧录

按各项目组正常内核编译打包流程重编即可。本案例用 aarch64 gcc 11.4 与 14.3 均编过，4 个目标文件零警告。

### 5.2 老化/压测

- dmesg 自开机起 `no core match` 计数为 0：
  `dmesg | grep -c "no core match"` → `0`
- demo 日志出现：
  `Use DMA heap /dev/dma_heap/system-uncached-dma32 for pressure buffers only`
- pressure 压测统计全部成功（本板实测参考）：
  `[RGA pressure70] elapsed=240s ... attempted=2753 success=2753 errors=0 failed_jobs=0 rga2_tasks=154168 rga3_tasks=8259`

### 5.3 一个容易吓到自己的点

开机 log 里 `Memory: ... DMA32 empty` 是**正常的**：RK3588 arm64 把 <4G 划给了 ZONE_DMA，ZONE_DMA32 为空。GFP_DMA32 分配会沿 zonelist 回退进 ZONE_DMA，拿到的物理页依然 <4G——正是 RGA2 需要的。不要因为这个去调 zone 配置。

### 5.4 内核态 RGA 调试手段（排查其它 RGA 问题用）

```bash
# 需要 CONFIG_ROCKCHIP_RGA_DEBUGGER + CONFIG_DEBUG_FS
echo msg > /sys/kernel/debug/rkrga/debug        # 打开策略日志
# 复跑用例，dmesg 会逐核打印匹配/拒绝原因：
#   feature / rd_mode / resolution(RGA3 限 68x2~8176x8176) / CSC / rotate /
#   "RGA2 only support under 4G memory!"
# 正常时 RGA2-only 任务应见: matched cores = 0x4（RGA3 两核 = 0x3，全核 = 0x7）
cat /sys/kernel/debug/rkrga/scheduler_status    # 各核状态/负载
```

## 6. 背景知识

- **标准 heap vs rk 私有 heap**：`/dev/dma_heap/<name>`（标准 `dma_heap_add()` + `DMA_HEAP_IOCTL_ALLOC`）是 librga/MPP 等存量用户态依赖的接口；`/dev/rk_dma_heap/<name>`（`rk_dma_heap_add()` + `'R'` magic ioctl）是 Rockchip 新框架，供新用户态使用。两者共存，互不冲突，本文修复不影响后者。
- **RGA3 vs RGA2 关键差异**：RGA3 分辨率范围 68×2 ~ 8176×8176（最小宽 68）；RGA2 MMU 仅 32 位寻址（缓冲必须 <4G）；RGA3 不支持 YUV422 旋转 90/270。压测用例正是利用这些差异构造"仅某核可跑"的任务来分别压测。
- **核心掩码**：RGA3_core0=0x1，RGA3_core1=0x2，RGA2=0x4，全核=0x7。
- **教训**：SDK 分支合并/迁移时，"源码在、Makefile 不编、库文件丢失"的死代码极易留下——它编译期不报错、运行期才以各种外设老化失败的形式暴露。合入 6.x 大版本时，建议对 `drivers/dma-buf/heaps/` 这类有孤儿文件的目录做一次 `obj-*` 与源文件的一致性核对。
