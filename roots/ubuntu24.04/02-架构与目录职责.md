# 02 架构与目录职责

## 1. 设计思想

把"构建一个 rootfs"拆成**可重放的分步流水线**:

1. **基础包** (base-package/) 提供最小可启动的骨架 (ubuntu-base 官方 tar);
2. **功能组** (chroot/$SPACE_NAME/<组>/) 在骨架上按序叠加正交能力
   (系统基础 → 桌面 → Rockchip 硬件支持 → OEM 定制 → 清理);
3. **配置** (config/<profile>) 只是"基础包 + 功能组序列"的菜单, 不含逻辑;
4. 所有执行逻辑集中在 `lib/lib.sh`, 入口 `build.sh` 只负责按序调用。

由此得到三个性质:

- **组合性**: 新做一个产品 = 新写一个 config + 按需复用功能组, 不改核心代码;
- **可重入**: 每步成功即在 btrfs 快照池打只读快照 + 更新进度标记, 失败/断电自动续跑;
- **构建机无痕**: 构建期注入的挂载/网络/缓存, 打包前全部还原, 镜像不携带构建机痕迹。

## 2. 三层架构

```
┌────────────────────────────────────────────────────────────┐
│ 配置层  config/<profile>  —— 纯数据, 5 个环境变量             │
│   PACKAGE_NAME / SPACE_NAME / DO_LIST /                     │
│   SOURCE_LIST_FILE / IMAGE_NAME                             │
│   .config 符号链接选择当前 profile (本机状态, 不提交)           │
├────────────────────────────────────────────────────────────┤
│ 流程层  build.sh + lib/lib.sh                               │
│   build.sh: 入口、参数路由 (config/resume/clean-pool)        │
│   lib.sh  : 全部机制 —— trap、断点续跑、本地源加速、            │
│             apt 缓存、基础包解包、chroot 执行器、打包          │
├────────────────────────────────────────────────────────────┤
│ 内容层  chroot/$SPACE_NAME/<功能组>/NN_desc.{apt,shell,overlay}│
│   文件名字典序 = 执行顺序; 失败即中断                          │
└────────────────────────────────────────────────────────────┘
        资源侧: res/(apt源)  base-package/(基础包)  tools/(挂载工具)
        供应链: src_deb/ 子模块 (自编译 deb 源码 + firefly reprepro 镜像仓库)
```

## 3. 目录职责

| 路径 | 职责 |
| --- | --- |
| `build.sh` | 构建入口 (55 行): 导出 TOP_DIR → configure → sync_firefly_repo → pre_base → 本地源 → 换 apt 源 → do_list → do_clean → do_package |
| `lib/lib.sh` | 核心库 (1181 行, **读它=读懂本仓库**): 快照池管理、进度标记、chroot 执行器、加速、缓存、打包、交互菜单、trap 体系 |
| `config/` | 6 个配置 profile + `.config` 符号链接 (kylin_common 为隐藏 legacy) |
| `chroot/` | 功能组步骤库: 三个 SPACE (`ubuntu24` / `kylin` / `kylin_general`) + `scripts/do_apt.sh` |
| `res/` | apt 源文件: `res/ubuntu24/ubuntu.sources` (阿里云 noble ports, deb822 格式); `res/kylin/` 刻意留空 (麒麟镜像自带官方源) |
| `base-package/` | 基础 rootfs 包 (数 GB, 不入 git) |
| `src_deb/` | 自编译 deb 源码 (git submodule) + firefly reprepro 仓库镜像 |
| `tools/mount-rootfs.sh` | 手动向 rootfs 目录挂/卸 proc、sysfs、/dev、/dev/pts (`-m` 挂 / `-u` 卸) |
| `tools/qemu_reg` | 手动向 binfmt_misc 注册 aarch64 转译 (一般用不到, pre_base 用 update-binfmts) |
| `aidocs/` | 仓库权威文档中心 (架构性修改必须同步更新) |
| `output/` | 全部生成物: `btrfs_pool.img`(快照池) `btrfs_mnt/`(池挂载点) `log/` `apt_cache/` `mnt/`(打包挂载点) `*.img`(成品) |

**运行期散件**:

| 文件 | 说明 |
| --- | --- |
| `.build_progress` (仓库根) | 实时进度标记: 内容=最后完成步骤全名 (特殊值 `000_pre_base`=基础层就绪); 每步成功原子更新; 构建成功自动清除; 删除即全新构建 |
| `output/btrfs_pool.img` | btrfs 快照池 (稀疏 loop 镜像): `base/`(基础包解包层) + `work/`(构建工作子卷) + `snap/<步骤全名>/`(每步只读快照) |
| `/etc/ffgo/ffver` (产物内) | 镜像元数据: `FIREFLY: <commit 前 10 位>` + 构建时间 + 构建者 —— 用它确认镜像对应哪次提交 |

## 4. 一次构建的数据流

```
base-package/ubuntu-base-24.04.3-base-arm64.tar.gz
        │ pre_base: 解包到快照池 base 子卷, 再 snapshot 出可写 work
        ▼
output/btrfs_mnt/work/                    ← 构建工作目录 (= 将来镜像的根)
   + usr/bin/qemu-aarch64-static          ← pre_base 注入 (转译 arm64)
   + etc/resolv.conf + ssl certs          ← 宿主网络/CA 注入
   + proc sys dev dev/pts 挂载            ← tools/mount-rootfs.sh -m
   + var/cache/apt/archives ⇄ output/apt_cache  (bind-mount 缓存)
   + etc/hosts += "127.0.0.1 wiki.t-firefly.com" (本地源劫持)
        │ do_list: 按 DO_LIST 顺序 chroot 执行各功能组步骤
        │   res/ubuntu24/ubuntu.sources → etc/apt/sources.list.d/
        │   firefly 源 (本地 reprepro) → libmali/mpp/gstreamer-rockchip...
        │   (每步成功: 打只读快照 + 更新 .build_progress)
        ▼
do_clean: 卸 apt 缓存 bind → 还原 hosts → 删 /chroot → apt autoclean
        → 还原 resolv.conf 符号链接 → 卸 proc/sys/dev
        ▼
do_package: du 估容 ×1.2 → dd 稀疏建文件 → mkfs.ext4 → loop 挂载 cp -a
        ▼
output/<IMAGE_NAME>-<YYYYMMDD>-<HHMM>.img
```

## 5. 自编译包供应链 (src_deb/)

两层关系:

1. 构建期 `firefly-pre/1_apt-source.shell` 在 rootfs 内把 apt 源设为
   `http://wiki.t-firefly.com/firefly-ubuntu-repo`, pin 优先级 **1001**
   (允许 firefly 的旧版本包覆盖 Ubuntu 同名新版本);
2. 本地加速机制把该域名劫持到宿主 80 端口的 `firefly-reprepro` 镜像,
   URL 与 GPG 签名验证完全不变。

**"改一个 firefly 包"的正确路径** (不要在构建步骤里硬塞 deb):

```
改对应子模块源码 → 打 deb → 按 reprepro 规则放进
src_deb/firefly-reprepro/firefly-ubuntu-repo/ → 重建仓库索引
→ (发布时才需要) sync.sh rsync 推到官方服务器
```
