# 问题解决过程：AIBOX-PRO 启动延迟修复

- 解决日期：2026-08-03
- 环境：SpacemiT K3、Firefly AIBOX-K3/AIBOX-PRO-K3、K3 Linux SDK 6.18、U-Boot 2022.10、ESOS RT24 双 RCPU、UFS 启动

## 问题现象

开发板 EEPROM 中写入 `k3-firefly-aibox-k3` 时，SPL、U-Boot、Linux 和根文件系统均可正常启动。

最初将 EEPROM 产品名改为 `k3-firefly-aibox-pro` 后，U-Boot FIT 中没有对应 configuration，SPL 回退到默认 `k3_deb1`，启动日志显示 `Model: spacemit k3 deb1 board`，并错误启用 eSPI 等 DEB1 配置。

补齐 U-Boot PRO FIT 配置后，系统已经能够进入根文件系统，但在 `DDR quick boot consume 9ms` 之后、U-Boot proper banner 输出之前仍固定无日志停顿约 12 秒：

- `k3-firefly-aibox-k3`：U-Boot 第一个时间戳约为 `[1.055]`。
- `k3-firefly-aibox-pro`：U-Boot 第一个时间戳约为 `[12.971]`。
- 固定差值约为 11.916 秒。

## 最终根因

问题包含两个连续根因：

1. U-Boot FIT 未包含 `k3-firefly-aibox-pro` 的 DTB image 和 configuration，导致 SPL 按 EEPROM 产品名匹配失败并使用默认 `k3_deb1`。
2. ESOS FIT 只包含 `k3-firefly-aibox-k3` 的 RCPU0/RCPU1 DTB。SPL 会把 EEPROM 的真实 `product_name` 写入 `rcpu-data-null` 共享内存；当产品名为 `k3-firefly-aibox-pro` 时，两个 RCPU 固件均找不到 `model` 完全匹配的 DTB，无法完成启动同步。

ESOS 的 `rt_hw_board_init()` 从固定地址开始无限扫描 DTB 表，只有当 DTB 根节点 `model` 与共享内存中的产品名完全相同，并且 CPU `reg` 与当前 hart ID 相符时才会退出扫描并继续初始化。

U-Boot 的 `k3_rproc_start()` 对每个 RCPU 使用约 6000 次 `mdelay(1)` 等待同步标志。RCPU0 和 RCPU1 均无法完成初始化时，两个 6 秒等待累计约 12 秒。超时后驱动仍返回 0，所以 SPL 继续进入 U-Boot proper，表现为“无日志卡十几秒后继续启动”。

## 关键排查过程

1. 对比 `aibox.log` 和 `aibox-pro.log`，确认进入 U-Boot proper 后的设备探测、环境加载、UFS、显示、内核、DTB 和 ramdisk 加载耗时几乎相同，排除 UFS、DP、环境变量和 Linux 启动阶段。
2. 延迟只发生在 SPL 完成 DDR 初始化之后、U-Boot proper 输出 banner 之前，因此将范围缩小到 SPL 后半段的 FIT loadables 加载和协处理器启动。
3. 确认 U-Boot FIT 原本没有 PRO configuration，增加 `fdt_15` 和 `conf_15` 后，日志中的板型从错误的 `k3 deb1` 修正为 `spacemit AIBOX-PRO-K3 board`。
4. 检查 SPL 代码，发现 `board_spl_fit_image_post_load()` 会将 EEPROM 产品名原样复制到 ESOS 共享内存，RCPU firmware 随后通过 `rproc_load()` 和 `rproc_start()` 启动。
5. 检查 ESOS FIT 和设备树，确认原镜像只包含两个 `model = "k3-firefly-aibox-k3"` 的 AIBOX DTB，不包含 `k3-firefly-aibox-pro`。
6. 检查 ESOS `board.c`，确认其设备树选择使用严格字符串比较并在未匹配时持续扫描。
7. 检查 `drivers/remoteproc/k3-rproc.c`，发现 Core0 和 Core1 各有约 6000 ms 的同步等待，累计时间与日志中的 11.916 秒高度吻合，形成完整证据链。
8. 曾在 BootROM `DFU download` 状态下尝试 `fastboot flash uboot`，设备未处于真正的 U-Boot fastboot 模式，且 raw FIT 被主机 fastboot 错误按 sparse 方式处理，不能作为有效烧录验证。最终使用重新生成的整包进行验证。

## 解决方案

1. 在 U-Boot 中新增 `k3-firefly-aibox-pro.dtb`，加入 K3 DTB 编译列表。
2. 在 `uboot_fdt.its` 中增加 `fdt_15` 和 `conf_15`，configuration description 精确使用 EEPROM 产品名 `k3-firefly-aibox-pro`。
3. 在 ESOS 中分别从 RCPU0、RCPU1 的 AIBOX-K3 DTS 创建对应的 AIBOX-PRO DTS，将根节点 `model` 修改为 `k3-firefly-aibox-pro`。
4. 在 `esos_rt24.its` 中增加两个 PRO DTB image，地址使用 DTB 表连续的 50 KiB 槽位 `0x100f4a000` 和 `0x100f56800`。
5. 将两个新 DTB 加入 `conf_dual.loadables`，并放在 RCPU firmware 之前加载。
6. 清理 ESOS Buildroot 缓存后重新编译 U-Boot、ESOS 和整包镜像。

详细代码见 `01-代码修改记录.md`。

## 验证结果

- 验证方法：EEPROM 写入 `k3-firefly-aibox-pro`，重新整包烧录，观察 SPL/U-Boot 串口日志并进入 Linux 根文件系统。
- U-Boot FIT 验证：构建输出包含 `Configuration 14 (conf_15)`，description 为 `k3-firefly-aibox-pro`，FDT 指向 `fdt_15`。
- ESOS FIT 验证：最终 `esos.itb` 包含 `rcpu0-dtb-aibox-pro-k3`、`rcpu1-dtb-aibox-pro-k3` 和两个 `model = "k3-firefly-aibox-pro"` 的 DTB。
- 镜像验证：最终 `esos.itb` SHA256 为 `a9fcdd5b7905cd331845dfe702346069530f165dc2a401f5c9948ae64c7d09dd`。
- 运行结果：用户确认修改和整包烧录后问题已经成功解决。

## 可复用经验

- EEPROM 板型字符串可能同时参与 AP U-Boot FIT 和协处理器固件 DTB 选择，新增产品名时必须检查所有消费者，不能只增加 Linux 或 U-Boot DTB。
- 固定约 12 秒的无日志延迟应优先搜索两个串行的 6 秒超时或双核逐个等待路径，而不是将问题归因于存储读取速度。
- Buildroot 本地源码包可能因构建目录和 stamp 缓存而未同步修改；修改 ESOS 这类 local package 后，使用 `esos-dirclean` 再构建更可靠。
