# 问题解决过程：AIBOX-PRO USB Host设备树移植

- 解决日期：2026-08-10
- SoC：SpacemiT K3
- 板卡：Firefly AIBOX-PRO
- SDK：K3 Linux SDK 6.18
- 内核日志版本：Linux 6.18.3
- 外部Hub：Genesys Logic GL3523
- USB2多路复用器：SGM7227YMS
- 测试设备：USB 2.0 U盘
- 最终状态：用户明确确认测试正常

## 1. 问题现象

AIBOX-PRO参考AIBOX设备树迁移USB Host。AIBOX中K3 USB3 Port A原本用于Type-C；AIBOX-PRO硬件把同一组USB2 D+/D-和USB3 RX/TX差分信号连接到板载GL3523，再由GL3523扩展到两个USB Host接口。

最初现象：

- USB口插入USB 2.0 U盘后，`lsblk`看不到新磁盘。
- xHCI、USB2 PHY、USB3 PHY可以启动。
- 排查中曾出现GL3523的USB3一侧能够以5Gbps枚举，但USB2 companion Hub不出现，因此USB 2.0 U盘仍不可用。
- 修改GPIO控制后，后续日志中GL3523完全消失，`lsusb -t`只剩两个xHCI根Hub：

```text
/:  Bus 001.Port 001: Dev 001, Class=root_hub, Driver=xhci-hcd/1p, 480M
/:  Bus 002.Port 001: Dev 001, Class=root_hub, Driver=xhci-hcd/1p, 5000M
```

这说明USB控制器本身正常，但控制器和GL3523之间没有任何有效下游设备完成连接或枚举。

## 2. 最终根因

最终不是单一软件驱动问题，而是设备树必须同时满足以下硬件条件。

### 2.1 GL3523复位极性经过Q8反相

`USB30_HUB_RST`连接Q8 NMOS栅极，GL3523的`HUB_RESET#`位于Q8漏极并由R118上拉。

- GPIO77高：Q8导通，`HUB_RESET#`低，GL3523保持复位。
- GPIO77低：Q8截止，`HUB_RESET#`高，GL3523释放复位。

错误的`output-high`会把GL3523永久保持在复位状态。这是“修改后整个Hub直接消失”的直接原因。

### 2.2 USB2 D+/D-必须通过GPIO118选择GL3523路径

K3 USB2 D+/D-经过SGM7227：

- `USB_SEL = 1`：HSD2导通，连接GL3523 USB2上行端口。
- `USB_SEL = 0`：HSD1导通，连接原Type-C/OTG路径。

GPIO118没有保持高电平时，USB3 SuperSpeed链路可能仍能出现，但USB2 companion Hub和USB 2.0 U盘不会枚举。

### 2.3 GPIO hog层级必须正确

`gpio-hog`节点必须是`&gpio`的直接子节点。放在根节点`/`下面只会成为普通设备树节点，GPIO核心不会把它作为hog申请和驱动。

### 2.4 GPIO100/118与UART1共享GPIO5电源域

K3 GPIO99～127共用GPIO5 I/O电源域。GPIO100、118、120、121不能分别使用3300和1800。结合UART1原理图的`VCC1V8_SYS`，最终统一GPIO100、118、120、121为1.8V。

### 2.5 UART1原四线pinctrl占用了GPIO118

公共`uart1_1_cfg`包含GPIO118 RTS、GPIO119 CTS、GPIO120 RX、GPIO121 TX。AIBOX-PRO RS232硬件只有RX/TX；继续使用四线组会让GPIO118被复用成UART1_RTS，直接破坏USB_SEL。

最终UART1改用只包含GPIO120/121的两线pinctrl。

## 3. 关键排查过程

### 3.1 先区分控制器问题和下游Hub问题

日志确认：

```text
xhci-hcd xhci-hcd.2.auto: new USB bus registered, assigned bus number 1
xhci-hcd xhci-hcd.2.auto: new USB bus registered, assigned bus number 2
xhci-hcd xhci-hcd.2.auto: Host supports USB 3.0 SuperSpeed
hub 1-0:1.0: USB hub found
hub 2-0:1.0: USB hub found
```

结论：

- DWC3/xHCI驱动已加载。
- USB2和USB3根Hub存在。
- PHY初始化正常。
- 不需要优先修改USB存储驱动。
- 故障范围缩小到GL3523供电、复位、USB_SEL或物理链路。

### 3.2 根据“USB3有、USB2无”定位USB_SEL

GL3523 USB3差分信号直接连接K3 USB3 PHY，而USB2 D+/D-经过SGM7227。只有USB3一侧枚举、USB2 companion Hub不出现时，最符合硬件拓扑的故障点是SGM7227选择状态。

因此增加GPIO118 hog并保持高电平，使D+/D-固定连接GL3523。

### 3.3 修正GPIO hog层级

检查设备树后发现GPIO hog不在GPIO控制器节点下面。将GPIO77和GPIO118 hog移动到：

```dts
&gpio {
	...
};
```

避免配置看似存在、运行时GPIO却未被驱动。

### 3.4 GL3523完全消失后重新检查复位硬件

最新失败日志中没有任何GL3523 Vendor/Product或下游Hub信息，只剩根Hub。对照`K3-AIBOX-PRO.pdf`最后几页原理图发现：GPIO77控制的是Q8栅极，不是直接控制`HUB_RESET#`。

设备树当时配置：

```dts
output-high;
```

这会导通Q8并把GL3523持续复位。改为：

```dts
output-low;
```

后，GL3523可释放复位。

### 3.5 检查RS232修改避免重新引入冲突

用户同时迁移UART1 RS232。检查确认UART1已改成GPIO120/121两线组，不再包含GPIO118。启动日志中的：

```text
f0612000.serial: ttyS1 ... is a XScale
```

说明UART1控制器注册；更重要的是最终pinctrl不再抢占USB_SEL。

### 3.6 编译并进行板端验证

最终设备树通过`cpp + dtc`检查。用户编译、烧写并执行板端测试后明确回复“测试正常”，确认最终配置有效。

## 4. 最终解决方案

最终配置要点：

1. GPIO100使用fixed regulator，高电平打开USB口5V。
2. GPIO77作为GPIO hog保持低电平，释放GL3523复位。
3. GPIO118作为GPIO hog保持高电平，选择SGM7227的GL3523通道。
4. GPIO100和GPIO118使用`power-source = <1800>`。
5. GPIO77保留`power-source = <3300>`。
6. 启用`usb3_porta_u2phy`。
7. 启用`usb3_porta_u3phy`。
8. `usb3_porta`固定`dr_mode = "host"`并引用5V regulator。
9. GPIO hog必须位于`&gpio`下。
10. UART1只使用GPIO120/121，不得占用GPIO118。

完整代码见同目录的`01-代码修改记录.md`。

## 5. 在另一台开发环境一次性移植的检查清单

按顺序执行，不要跳过。

### 5.1 确认硬件版本一致

必须确认目标板仍是相同AIBOX-PRO硬件连接：

- GPIO100连接`USB30_VCC5V0_EN`。
- GPIO77经过Q8连接GL3523 `HUB_RESET#`。
- GPIO118连接SGM7227 `USB_SEL`。
- K3 USB3 Port A的USB2 D+/D-连接SGM7227公共端。
- SGM7227 HSD2连接GL3523 USB2上行端口。
- K3 USB3 Port A SuperSpeed RX/TX连接GL3523上行端口。

如果目标板更换了反相管、USB mux通道或GPIO编号，不能直接复制电平配置。

### 5.2 复制设备树文件

在目标SDK的`arch/riscv/boot/dts/spacemit/`目录执行或人工复制：

- `k3-firefly-aibox-pro.dts`
- `k3-firefly-aibox-pro.dtsi`
- `aibox-pro-test.dtsi`

复制后确认：

```bash
rg -n 'FF_USB30_HOST|aibox-pro-test.dtsi' k3-firefly-aibox-pro.dts
rg -n 'output-low|usb_sel_host|K3_GPIO\(100\)|K3_GPIO\(118\)' aibox-pro-test.dtsi
```

### 5.3 加入DTB构建目标

`Makefile`必须包含：

```makefile
dtb-$(CONFIG_SOC_SPACEMIT_K3) += k3-firefly-aibox-pro.dtb
```

### 5.4 全局检查引脚冲突

在设备树目录执行：

```bash
rg -n 'K3_PADCONF\((77|100|118),|K3_GPIO\((77|100|118)\)' .
```

逐项确认：

- GPIO77只用于USB Hub复位。
- GPIO100只用于USB Host 5V使能。
- GPIO118只用于USB_SEL。
- UART1不能继续引用包含GPIO118的`uart1_1_cfg`。

还应检查最终展开后的设备树，而不是只检查单个源文件，因为公共DTSI和后包含的DTSI都可能覆盖属性。

### 5.5 检查共享电压域

执行：

```bash
rg -n -C 5 'K3_PADCONF\((100|118|120|121),' .
```

确认GPIO100、118、120、121最终均使用：

```dts
power-source = <1800>;
```

### 5.6 检查内核功能

目标内核至少需要具备：

- DWC3 Host支持。
- xHCI platform支持。
- SpacemiT K3 USB2 PHY驱动。
- SpacemiT K3 USB3 PHY驱动。
- USB mass storage。
- SCSI disk和块设备支持。
- fixed regulator和GPIO支持。

可从运行日志确认主要驱动是否工作：

```bash
dmesg | grep -iE 'xhci|dwc3|usb2.*phy|usb3.*phy|usb-storage|scsi'
```

### 5.7 编译DTB

使用项目脚本的快速设备树模式：

```bash
cd /path/to/K3_Linux_SDK_6.18
./aibox-pro-build.sh
```

不需要因为只修改DTS而执行内核全量重编译。

也可以在Linux源码树内单独验证DTS语法：

```bash
cd arch/riscv/boot/dts/spacemit

cpp -nostdinc \
  -I . \
  -I ../../../../../../include \
  -undef -D__DTS__ \
  -x assembler-with-cpp \
  k3-firefly-aibox-pro.dts \
  /tmp/k3-firefly-aibox-pro.pp.dts

dtc -I dts -O dtb \
  -o /tmp/k3-firefly-aibox-pro.dtb \
  /tmp/k3-firefly-aibox-pro.pp.dts
```

### 5.8 烧写前检查最终DTB

推荐反编译最终要打包的DTB：

```bash
dtc -I dtb -O dts \
  -o /tmp/k3-firefly-aibox-pro.final.dts \
  /path/to/k3-firefly-aibox-pro.dtb

rg -n -C 8 'usb30-hub-rst-hog|usb-sel-host-hog|usb3@cad00000|phy@cad20000|phy@cad30000' \
  /tmp/k3-firefly-aibox-pro.final.dts
```

最终DTB必须看到：

```text
usb30-hub-rst-hog -> output-low
usb-sel-host-hog  -> output-high
phy@cad20000      -> status = "okay"
phy@cad30000      -> status = "okay"
usb3@cad00000     -> status = "okay"
usb3@cad00000     -> dr_mode = "host"
```

确认板型：

```bash
fdtget -t s /path/to/k3-firefly-aibox-pro.dtb / model
```

预期：

```text
spacemit AIBOX-PRO-K3 board
```

### 5.9 确认烧写的确是新DTB

启动后执行：

```bash
tr -d '\0' </proc/device-tree/model
```

预期输出：

```text
spacemit AIBOX-PRO-K3 board
```

如果输出仍是旧板型，不要继续调驱动，应先修正bootfs中的DTB选择和打包。

## 6. 板端逐级验证

### 6.1 第一级：检查物理控制信号

有条件时用万用表或示波器确认：

| 测试点 | 正常值 | 异常含义 |
| --- | --- | --- |
| USB接口VBUS | 约5V | GPIO100或电源开关配置错误 |
| GPIO77 / `USB30_HUB_RST` | 低电平 | 高电平会让Q8导通并复位GL3523 |
| GL3523 `HUB_RESET#` | 高电平 | 低电平说明GL3523仍在复位 |
| GPIO118 / `USB_SEL` | 高电平，GPIO域1.8V | 低电平说明D+/D-仍走OTG路径 |

如果系统带`gpioinfo`：

```bash
gpioinfo | grep -E 'usb30_hub_rst|usb_sel_host'
```

应能看到两个GPIO被hog占用并标记为输出。

### 6.2 第二级：检查xHCI根Hub

```bash
dmesg | grep -iE 'xhci|Host supports USB 3.0|root hub'
lsusb -t
```

至少应先看到：

```text
480M  USB2 root_hub
5000M USB3 root_hub
```

如果根Hub都没有，检查`usb3_porta`、两个PHY、时钟、复位和内核驱动；此时不要先检查GL3523 GPIO。

### 6.3 第三级：检查GL3523 companion Hub

正常情况下，USB2和USB3根Hub下面应分别出现GL3523对应的下游Hub。典型树形结构类似：

```text
/:  Bus 001.Port 001: Dev 001, Class=root_hub, Driver=xhci-hcd/1p, 480M
    |__ Port 001: Dev 002, Class=Hub, Driver=hub/4p, 480M
/:  Bus 002.Port 001: Dev 001, Class=root_hub, Driver=xhci-hcd/1p, 5000M
    |__ Port 001: Dev 002, Class=Hub, Driver=hub/4p, 5000M
```

具体端口数和设备号以GL3523固件及实际连接为准。

### 6.4 第四级：检查USB 2.0 U盘枚举

插入U盘前运行：

```bash
dmesg -w
```

另一个终端运行：

```bash
lsusb
lsusb -t
lsblk -o NAME,MAJ:MIN,RM,SIZE,RO,TYPE,FSTYPE,MOUNTPOINTS,TRAN,MODEL
```

预期过程：

1. USB2端口报告`new high-speed USB device`或相应速度。
2. `usb-storage`或`uas`绑定。
3. SCSI层创建新的`sdX`。
4. `lsblk`出现可移动磁盘及分区。

### 6.5 第五级：安全读写测试

先用`lsblk`确认U盘设备和分区，绝对不要把系统盘`/dev/sda`误当成U盘。以下`/dev/sdX1`必须替换为实际U盘分区；不执行格式化操作。

```bash
mkdir -p /mnt/usb-host-test
mount /dev/sdX1 /mnt/usb-host-test

dd if=/dev/urandom \
  of=/mnt/usb-host-test/aibox-pro-usb-test.bin \
  bs=1M count=64 conv=fsync

sha256sum /mnt/usb-host-test/aibox-pro-usb-test.bin
cp /mnt/usb-host-test/aibox-pro-usb-test.bin /tmp/aibox-pro-usb-test.readback.bin
sha256sum /tmp/aibox-pro-usb-test.readback.bin

sync
rm /mnt/usb-host-test/aibox-pro-usb-test.bin
umount /mnt/usb-host-test
rm /tmp/aibox-pro-usb-test.readback.bin
```

两次SHA-256必须一致。测试过程中同时检查：

```bash
dmesg | tail -100
```

不应出现USB reset、I/O error、SCSI abort、device descriptor read error或文件系统错误。

## 7. 故障现象快速对照表

| 现象 | 最可能原因 | 优先检查 |
| --- | --- | --- |
| `lsusb -t`连根Hub都没有 | DWC3/xHCI/PHY未启用 | `usb3_porta`、U2/U3 PHY、内核配置、DTB是否烧写 |
| 只有480M和5000M根Hub，没有GL3523 | Hub未供电或仍在复位 | GPIO100、GPIO77、VBUS、`HUB_RESET#` |
| 只出现GL3523 USB3 Hub，不出现USB2 companion Hub | USB_SEL或D+/D-路径错误 | GPIO118必须高、SGM7227 HSD2、USB0_DP/DN |
| Hub正常但插U盘没反应 | 下游端口VBUS或接口布线问题 | USB口5V、连接器D+/D-、ESD器件、Hub下游端口 |
| U盘出现在`lsusb`但不在`lsblk` | 存储/SCSI驱动缺失 | `usb-storage`/`uas`、SCSI disk、内核配置 |
| 开启RS232后USB2突然失效 | UART1抢占GPIO118 | 禁止使用四线`uart1_1_cfg`，改成GPIO120/121两线组 |
| 冷启动偶尔成功、热启动失败 | Hub复位时序或实际电平不稳定 | 示波器检查GPIO77、`HUB_RESET#`和电源上升时序 |
| 编译成功但行为完全不变 | 仍启动旧DTB | `/proc/device-tree/model`、bootfs内容、最终DTB时间和哈希 |

## 9. 可复用经验

- 不要只根据网络名中的`RST`或低有效后缀判断SoC GPIO电平，必须沿原理图检查中间三极管、MOS管和反相器；本例GPIO高反而会断掉整个Hub。
- USB3 Hub同时包含USB2 companion链路和USB3 SuperSpeed链路。出现“USB3 Hub有、USB2 U盘无”时，应优先比较两条物理路径的差异，本例差异点就是SGM7227。
- GPIO hog必须位于GPIO控制器节点下；DTC语法通过并不代表GPIO hog会被Linux解析。
- pinctrl不仅决定复用功能，还可能修改共享I/O电源域。相邻GPIO配置成不同`power-source`时，应先检查SoC驱动中的电源域映射。
- 外设移植完成后必须全局检查引脚复用冲突。UART控制器即使不启用硬件流控，四线pinctrl仍会占用RTS/CTS引脚。
- 判断USB故障应逐层进行：PHY/控制器 → 根Hub → 板载Hub → USB设备 → SCSI块设备 → 文件系统读写。每一层都有明确日志证据，可以避免盲目修改驱动。
