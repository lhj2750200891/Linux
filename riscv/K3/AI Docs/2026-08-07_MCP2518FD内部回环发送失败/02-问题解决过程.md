# 问题解决过程：MCP2518FD 内部回环发送失败

- 解决日期：2026-08-07
- 环境：Spacemi K3、Firefly AIBOX-PRO、Linux 6.18、MCP2518FD、SPI4
- CAN 配置：仲裁波特率 500000 bit/s，数据波特率 2000000 bit/s

## 问题现象

MCP2518FD 驱动能够正常探测，系统创建了 `can0`：

```text
mcp251xfd spi4.0 can0: MCP2518FD ... successfully initialized.
```

基础检查全部通过，CAN 接口可以进入 `ERROR-ACTIVE` 和内部回环模式，`cansend` 命令也返回成功，但最初的回环测试存在以下现象：

```text
回环接收超时
TX packets 增量=0
RX packets 增量=0
spi4.0 IRQ 增量=0
后续发送出现 TX dropped
```

另外，在整理 `aibox-pro-test.dtsi` 时曾因重复包含公共 DTSI 出现：

```text
Error: arch/riscv/boot/dts/spacemit/k3.dtsi:4.1-9 syntax error
FATAL ERROR: Unable to parse input tree
```

## 最终根因

K1 SPI 控制器驱动使用自定义 `transfer_one_message()`，在整个 SPI message 期间持续设置 `TOP_HOLD_FRAME_LOW`，但没有处理每个 `spi_transfer` 的 `cs_change` 属性。

MCP2518FD 发送一帧时，驱动构造两个 transfer：

1. 写 CAN 帧数据到 TX RAM。
2. 写发送 FIFO 的 `UINC | TXREQ`，请求控制器开始发送。

第一个 transfer 明确设置了 `cs_change = 1`。旧 K1 SPI 驱动没有在两个 transfer 之间释放再重新拉低 CS，导致 MCP2518FD 没有把第二段数据识别成新的 SPI 寄存器写命令，FIFO TXREQ 未被置位。

因此：

- CAN 帧没有进入 MCP2518FD 的实际发送流程。
- TX Event FIFO 没有发送完成事件。
- CAN_INT 没有被拉低。
- `/proc/interrupts` 中 `spi4.0` 子中断保持为 0。

IRQ 不增长是 TXREQ 命令未生效的结果，并不是 Linux GPIO 中断处理程序丢失了一个已经产生的中断。

## 关键排查过程

### 1. 确认驱动和 CAN 网络层基础状态

以下项目均正常：

- MCP2518FD 探测成功并创建 `can0`。
- `can0` 绑定到 `spi4.0`。
- CAN-FD 位时序配置成功。
- 控制器处于 `ERROR-ACTIVE`。
- 内部回环模式已经开启。

这排除了设备未绑定、时钟未启动、CAN 接口未启动等基础问题。

### 2. 观察发送统计和 MCP2518FD IRQ

`cansend` 返回成功只表示帧已经交给内核发送路径，不代表 MCP2518FD 已实际发送。测试时观察到：

```text
TX packets: 0 -> 0
RX packets: 0 -> 0
TX dropped 后续增加
spi4.0 IRQ: 0 -> 0
```

说明发送队列不能完成，后续帧最终因队列无法释放而被丢弃。

### 3. 读取 MCP2518FD 关键寄存器

读取结果：

```text
000: 024b0760
01c: bf1a0004
030: 00000000
040: 03000029
044: 00000000
048: 00000000
05c: ef000029
060: 00000000
064: 00000030
```

关键含义：

- `CiCON.OPMOD=2`：MCP2518FD 已经处于内部回环模式。
- `CiINT=0xbf1a0004`：只有 `TBCIF(bit2)`，没有 `TEFIF(bit4)`。
- `CiTXREQ=0`：没有 FIFO 处于发送请求状态。
- TEF 状态为空：没有形成发送完成事件。
- FIFO1 控制寄存器中的 `TXREQ(bit9)` 为 0。

寄存器证据表明故障发生在 MCP2518FD 接收发送请求之前，而不是发送完成之后的中断处理阶段。

### 4. 排除主控 SPI 控制器完全不工作

主控 SPI 控制器中断存在大量计数：

```text
39: ... 6087 ... c0885000.rspi0
40: ... 0    ... spi4.0
```

这说明 K1 SPI 控制器能够执行传输，MCP2518FD 的初始化和寄存器读取也进一步证明 SPI 总线基本通信正常。问题更可能与某一种 SPI message 组织方式有关，而不是 SPI4 整体不工作。

### 5. 沿 MCP2518FD 发送路径检查 SPI transfer

在 `mcp251xfd_ring_init_tx_obj()` 中确认：

```c
/* FIFO load */
xfer = &tx_obj->xfer[0];
xfer->tx_buf = &tx_obj->buf;
xfer->len = 0;
xfer->cs_change = 1;

/* FIFO request to send */
xfer = &tx_obj->xfer[1];
xfer->tx_buf = &ring->rts_buf;
xfer->len = rts_buf_len;
```

随后检查 `spi-spacemit-k1.c`，发现旧驱动遍历 transfer 时完全没有处理 `transfer->cs_change`，且通过 `TOP_HOLD_FRAME_LOW` 在整个 message 中保持 CS 有效。这与寄存器表现完全吻合：TX RAM 阶段之后的 FIFO TXREQ 命令未被芯片识别。

### 6. 关于 CAN_INT 5 V 电平

用户测得 CAN_INT 默认电平为 5.0 V。该电压是否超过 K3 GPIO 的绝对最大额定值仍需要根据原理图、电平转换器、上拉电源和芯片数据手册单独确认。

但本次内部回环失败的寄存器证据显示 MCP2518FD 根本没有产生发送完成事件，因此当时 IRQ 计数为 0 不能直接证明是电压域造成。SPI `cs_change` 修复后，在硬件没有改变的情况下 MCP2518FD IRQ 已从 0 增加到 1，进一步确认本次软件故障的直接根因是 SPI CS 时序。

## 解决方案

1. 在 `spi-spacemit-k1.c` 中增加 `k1_spi_set_cs()`，统一控制 `TOP_HOLD_FRAME_LOW`。
2. 在 `k1_spi_transfer_one_message()` 的 transfer 循环中处理 `transfer->cs_change`。
3. 当前 transfer 要求切换 CS 且不是最后一个 transfer 时：
   - 释放 CS。
   - 执行 `spi_transfer_cs_change_delay_exec()`。
   - 再次拉低 CS，开始下一条 SPI 命令。
4. 使用 `./aibox-pro-build.sh rebuild` 重新编译内核并更新 `bootfs.img`。
5. 烧录完整 `bootfs.img`，确保新 `Image` 被加载；只烧录 DTB 不能使 SPI 驱动修改生效。

详细代码对比见 `01-代码修改记录.md`。

- 测试期间无收发错误、无丢包。
- SPI CS 切换补丁解决了本次故障。

## 可复用经验

- `cansend` 返回成功只代表内核接受了帧，必须结合 TX/RX 统计、设备寄存器、TEF 和 IRQ 判断硬件是否真正发送。
- 一个 `spi_message` 内可以包含多条独立芯片命令；自定义 SPI 控制器驱动必须正确实现 `spi_transfer.cs_change`，不能无条件在整个 message 中保持 CS。
- 当外设 IRQ 不增长时，应先确认外设是否已经产生了可触发 IRQ 的事件；IRQ 为 0 可能是上游状态机没有运行，而不一定是 GPIO 中断配置错误。
