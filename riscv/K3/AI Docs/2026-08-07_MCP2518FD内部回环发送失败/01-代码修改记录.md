## 修改 1：K1 SPI 驱动处理 transfer 间的 CS 切换

文件：`drivers/spi/spi-spacemit-k1.c`  
位置：`k1_spi_transfer_one_message()` 附近

### 修改前

原驱动在整个 `spi_message` 开始时设置 `TOP_HOLD_FRAME_LOW`，在 message 完成后才清除。遍历 transfer 时没有检查 `transfer->cs_change`：

```c
static int k1_spi_transfer_one_message(struct spi_controller *host,
					       struct spi_message *message)
{
	struct k1_spi_driver_data *drv_data = spi_controller_get_devdata(host);
	struct completion *completion = &drv_data->completion;
	struct spi_transfer *transfer;
	u32 val;

	drv_data->message = message;

	message->status = 0;

	/* Hold frame low to avoid losing transferred data */
	val = readl(drv_data->base + SSP_TOP_CTRL);
	val |= TOP_HOLD_FRAME_LOW;
	writel(val, drv_data->base + SSP_TOP_CTRL);

	list_for_each_entry(transfer, &message->transfers, transfer_list) {
		reinit_completion(completion);

		if (!k1_spi_transfer_start(drv_data, transfer)) {
			message->status = -EIO;
			break;
		}

		k1_spi_transfer_wait(drv_data);
		k1_spi_transfer_end(drv_data, transfer);

		if (message->status)
			break;
	}

	drv_data->message = NULL;
	spi_finalize_current_message(drv_data->controller);

	val = readl(drv_data->base + SSP_TOP_CTRL);
	val &= ~TOP_HOLD_FRAME_LOW;
	writel(val, drv_data->base + SSP_TOP_CTRL);

	return 0;
}
```

MCP2518FD 的一帧发送由两个 SPI transfer 组成：

1. 第一个 transfer 将 CAN 帧写入 MCP2518FD TX RAM，并设置 `xfer->cs_change = 1`。
2. 第二个 transfer 写 FIFO 控制寄存器中的 `UINC | TXREQ`，要求芯片开始发送。

旧驱动持续保持 CS 为低电平，使第二个 transfer 的 SPI 命令没有形成新的命令帧，MCP2518FD 因而没有置位 TXREQ。

### 修改后

增加统一的 CS 控制函数：

```c
static void k1_spi_set_cs(struct k1_spi_driver_data *drv_data, bool enable)
{
	u32 val;

	val = readl(drv_data->base + SSP_TOP_CTRL);
	if (enable)
		val |= TOP_HOLD_FRAME_LOW;
	else
		val &= ~TOP_HOLD_FRAME_LOW;
	writel(val, drv_data->base + SSP_TOP_CTRL);
}
```

在每个 transfer 完成后检查 `cs_change`。如果当前 transfer 不是 message 的最后一个，则释放 CS、执行 SPI core 定义的 CS 延时，再重新选中器件：

```c
static int k1_spi_transfer_one_message(struct spi_controller *host,
					       struct spi_message *message)
{
	struct k1_spi_driver_data *drv_data = spi_controller_get_devdata(host);
	struct completion *completion = &drv_data->completion;
	struct spi_transfer *transfer;

	drv_data->message = message;
	message->status = 0;

	/* Hold frame low to avoid losing transferred data */
	k1_spi_set_cs(drv_data, true);

	list_for_each_entry(transfer, &message->transfers, transfer_list) {
		reinit_completion(completion);

		if (!k1_spi_transfer_start(drv_data, transfer)) {
			message->status = -EIO;
			break;
		}

		k1_spi_transfer_wait(drv_data);
		k1_spi_transfer_end(drv_data, transfer);

		if (message->status)
			break;

		if (transfer->cs_change &&
		    !list_is_last(&transfer->transfer_list, &message->transfers)) {
			k1_spi_set_cs(drv_data, false);
			spi_transfer_cs_change_delay_exec(message, transfer);
			k1_spi_set_cs(drv_data, true);
		}
	}

	drv_data->message = NULL;
	spi_finalize_current_message(drv_data->controller);
	k1_spi_set_cs(drv_data, false);

	return 0;
}
```

修改说明：MCP2518FD 能够把 TX RAM 写入和 FIFO TXREQ 写入识别成两条独立 SPI 命令，随后产生 TX Event FIFO 事件并通过 CAN_INT 触发中断。

## 修改 2：修正测试 DTSI 的包含关系

文件：`arch/riscv/boot/dts/spacemit/aibox-pro-test.dtsi`

### 修改前

测试 DTSI 曾再次包含公共设备树：

```dts
#include "k3-firefly-common.dtsi"
```

而 `k3-firefly-aibox-pro.dtsi` 所在的主设备树包含链已经包含该公共 DTSI，重复包含导致 DTC 报错：

```text
Error: arch/riscv/boot/dts/spacemit/k3.dtsi:4.1-9 syntax error
FATAL ERROR: Unable to parse input tree
```

### 修改后

删除 `aibox-pro-test.dtsi` 中重复的 `#include "k3-firefly-common.dtsi"`，让测试文件仅保存需要临时验证的节点覆盖。

同时在测试 DTSI 中增加：

```dts
#ifdef FF_SPI_CAN
&mcp251xfd
{
	compatible = "microchip,mcp2518fd";
};
#endif
```

修改说明：解决设备树重复包含造成的 DTC 语法错误，并把 MCP2518FD 型号覆盖限制在测试 DTSI 中。MCP2518FD 在修改 SPI 驱动前已经能够初始化，因此该 `compatible` 覆盖不是内部回环故障的最终根因。

## 修改 3：增强 CAN 测试脚本诊断能力

文件：`arch/riscv/boot/dts/spacemit/can_test.sh`

### 默认测试帧修改

修改前：

```sh
TEST_FRAME="${CAN_TEST_FRAME:-123#1122334455667788}"
```

修改后：

```sh
TEST_FRAME="${CAN_TEST_FRAME:-123##11122334455667788}"
```

其中第二个 `#` 表示 CAN-FD，紧随其后的 `1` 表示启用 BRS。

### 失败诊断增加

脚本在 TX、RX 或 MCP2518FD IRQ 不增长时，增加以下诊断输出：

```sh
grep 'spi4\.0' /proc/interrupts
grep -E 'gpio-56|spi4\.0|mcp251' /sys/kernel/debug/gpio
grep -E '^(01c|e04):' /sys/kernel/debug/regmap/spi4.0-crc/registers
```

修改说明：这些信息用于区分 CAN 网络层、MCP2518FD 控制器中断和主控 SPI 控制器传输问题。用户最终成功日志中的测试帧仍是 `123#1122334455667788`，因此测试成功直接验证的是 SPI 驱动修复，而不是默认 CAN-FD 测试帧修改。
